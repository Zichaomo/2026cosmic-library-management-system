## 结论

完整目标包含：多个应用实例安全写同一库、无按键自动刷新，以及异常退出后的可靠恢复。**当前课程白名单与已验证方案尚不能完整交付这三项。** rename竞争提供了一个可行的互斥原语线索，但不是完整锁协议；阻塞getch仍没有输入超时或后台刷新能力。

因此保留当前已验证的单进程合规应用（外部启动器独占句柄已于 2026-10-22 取消，单实例改为人工保证）。实验完成不等于业务竞争验收完成，两个终端抢最后一本书/同时注册/写入中断仍未实施。

## 实际工具链与文件实验

编译器：gcc (GCC) 16.1.0，目标：x86_64-w64-mingw32。探针PE实际导入KERNEL32.dll与msvcrt.dll。ASCII相对数据路径、全新独立目录重复执行，排除了中文绝对文件路径的干扰。本轮最终JSON：`build\concurrency\run-bac41e48542644dc93b11c85ab34efad/report.json`。

| 实验 | 实际结果 | 说明 |
| --- | --- | --- |
| wb首次/再次打开 | 均成功，SECOND覆盖FIRST | 不能作为占锁 |
| wb 24进程竞争 | 24成功，0拒绝 | 普通fopen不互斥 |
| wb持有期间另一个写者 | 成功 | 持有FILE*不等于独占句柄 |
| wx / wbx / w+bx新文件 | 三种均拒绝 | 本目标msvcrt运行库没有提供本实验所需x模式能力 |
| 各x模式24进程竞争 | 各0成功、24拒绝 | 不是“只有一个抢锁成功”，而是功能不可用 |
| wb持有子进程被kill | 文件仍在，普通wb仍能写 | 普通文件没有自动清除的锁语义 |
| rename 24个独立候选抢同一不存在目标 | 1成功、23拒绝 | 本地目标环境具备一次竞争的互斥效果 |
| rename成功进程退出后再次claim | 拒绝，目标文件仍在 | 残留占位不能自动判断是否可恢复 |
| 由测试明确释放rename目标到归档后再claim | 成功 | 正常释放/再获取路径成立；不是崩溃恢复 |

Microsoft当前CRT文档说明[fopen的x模式](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/fopen-wfopen?view=msvc-170)应拒绝已存在文件；这不证明本项目链接的msvcrt具有同样支持。这里以实际动态依赖与进程结果为准，也不外推到所有Windows/GCC/UCRT版本。

rename实验不是普通“先检查不存在再创建”，但仍缺少经过验证的唯一候选生成、所有权、释放与并发读写事务协议。不能因为过了24次竞争就把现有仓储直接置于该锁下开放多写者。进程退出遗留锁若按时间强制清理，可能把暂停或慢进程误判为死亡，形成双写；本轮没有采用这种恢复方法。目标仅本机当前文件系统，未证明网络盘/不同CRT行为。

## 输入与自动刷新

在真实ConPTY运行probe.exe input，先显示WAITING_FOR_GETCH；初始约10秒及随后约5秒输出检查期间进程保持运行、没有返回；输入A后显示GETCH_RETURNED 65并退出0。与[_getch官方说明](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/getch-getwch)的控制台单字符读取相符。

结合现有事件循环，当前代码等待getch返回后才能刷新仓储和画面。time只提供时间值，不是输入超时；循环检查time会引入忙等；本轮不引入kbhit、Sleep、线程或Win32等待API，也不把手动F5当作自动刷新。该实测证明当前输入路径的行为，不是对所有可能白名单算法的理论不可能性证明。
