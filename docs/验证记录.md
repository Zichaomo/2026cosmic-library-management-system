## 启动与终端修复

1. 独立导出源码在无本地脚本情况下可编译、首次准备样例；PE的CLR目录为空，是原生C程序。原build/library-data在make prepare前后哈希一致。
2. 用户连续报告输出失败。明确诊断记录为整帧6633字节、fwrite接受4088字节、ferror非零32；改小块后第二批fclose失败、已接受480字节。ferror是错误标志，不是errno，不能按“系统错误32”解释。
3. 纯C探针比较ASCII/中文、二进制/文本、fwrite/fputs/fputc，用户输出的中文均出现“涓枃…”乱码；据此发现程序运行时不是UTF-8。探针不读取图书馆数据，仅在build下写独立测试文本。
4. 在936下直接运行C程序，工具环境复现同样的6633/480/close失败和乱码；从同样936父环境调用新make run，因同一cmd命令中执行chcp 65001再启动，中文界面、管理员登录和Ctrl+Q退出0通过。
5. 用户在原Conda/PowerShell终端确认“这次可以了”。最终保留同cmd切编码和细分错误诊断，移除未解决根因的分块绕过，仍为整帧输出。未添加C的system/Win32，也不恢复PowerShell启动器。
6. 最终版重新编译和297项C断言通过；36个活动C源文件/头文件审计和43个旧参照哈希通过。make diagnose-console可再次查看环境和不同写入方式的结果，不纳入业务运行。

用户确认启动可用，未据此补写全部输入法、频闪、字体与业务人工验收。ConPTY工具主要用于I/O与退出码，不冒称用户120×35视觉验收。
